# 开发与验收

## 任务流程

先读项目工作约定和相关模块，确认用户要求与当前实现。需求模糊时先确认；明确需求直接完成。用 `git status` 区分已有修改与本轮改动，避免顺手重写整个文件或提交无关内容。

需要编辑游戏时，先执行 `doctor` 获取环境状况，再完成改动，最后执行 `check`。按下面的改动类型补充实际验收。没有明确要求时不编写单元测试，也不引入测试框架。

修复失败时先查看引擎日志中的首个有效错误。不要为让检查变绿而忽略全部错误、重置存档、移除正常资源或关闭必要机制。

## 按改动选择验收

| 改动 | 需要实际确认的路径 |
| --- | --- |
| 移动或键位 | 四套输入、连续移动、停步、拐弯、碰墙、拾取、按 Q / 使用道具、暂停后继续 |
| 泡泡与属性 | 普通十字、连锁、踢动、遥控、六种核心、预警与实际命中、同队与自伤、Bot 逃生 |
| 箱体 | 推箱空位与阻挡、装甲两次命中、宝库八次、一次跨四格只扣一点、奖励保留、坍塌与机关伤害 |
| 新地图或机关 | 八处出生点可离开、中央可连接、机关预警、泡泡被移动后的路径、随机选图、计时与逐圈坍塌 |
| PVE | 改动涉及的主任务、Bot 队友、出口、失败重试、复苏、支线奖章、Boss 半血与章节存档 |
| 美术与动画 | 四方向待机和走路、受击、困泡、放置、骑乘、出局、人物选择、图鉴与 HUD 裁切 |
| 天气与光照 | 白天到夜晚、常夜洞窟、随机固定火把、墙箱遮光、雾周期、照明弹八秒与火把二十秒 |
| 翻译 | 五种语言的大堂、图鉴、对白、动态数字占位符和长句排版，中文始终可切回 |
| 存档 | 旧文件加载、缺字段默认、保存再加载、两个模式分别推进、人物解锁与语言、退出记录 |
| 音乐 | 对应主题、完整循环、首尾接缝、静音保存、音效叠加及暂停行为 |
| 构建 | PCK 导出、产物运行、字体和语言 JSON、素材与授权文件、Git 不含缓存或可执行程序 |

单一机制改动先跑对应地图和相关组合；只有修改公共状态、地图生成、爆炸或剧情循环时，才需要扩大到全部地图和关卡。已有检查通过且没有新风险时，不反复跑同样内容。

## 保存证据

临时截图、对局记录、日志与检查存档放 `/tmp/paopaotang-*`。记录复现地图、模式、真人与 Bot 配置、操作和结果；画面问题还要记录昼夜、语言与角色。需要交付的少量配图再放入 `docs/screenshots/` 并由文档引用。

检查存档默认使用 harness 的独立路径。手工修改正常玩家存档前，先复制备份到 `/tmp`；验收后恢复，不通过重置玩家进度来绕开兼容性问题。

## 发布前

确认 README 与玩法说明没有把规划写成已完成功能。新增计数、图集布局、语言、剧情或命令时同步维护相应文档。导出排除开发工具与文档，仓库忽略运行时、安装包、根目录预览、导入缓存和本地存档。

只有用户要求提交或推送时才处理 Git。提交前看暂存清单，确认没有把已有无关修改、几十张临时截图或 `dist` 一起加入。推送后核对远端分支与本地提交。

交付说明报告实际改动、执行过的检查、证据目录与尚未覆盖的组合。导入和大厅启动通过时，明确说“启动检查通过”，不要替代成“全地图验收通过”。
